# VAJANS — Deployment Guide

Production hosting target: **Render** (Blueprint at `render.yaml`).
Database target: **Supabase** (Transaction pooler).

---

## 1. Architecture on Render

```
                          ┌─────────────────────────┐
                          │  vajans-frontend        │
   user ─── HTTPS ────────►  Static SPA (Vite/dist) │
                          └──────────┬──────────────┘
                                     │  XHR /api/*
                                     ▼
   ┌─────────────────────────────────────────────────────────┐
   │  vajans-backend  (web service, runs honcho)             │
   │  ┌────────────────────┐    ┌────────────────────────┐   │
   │  │ uvicorn app.main   │    │ celery worker          │   │
   │  │ (FastAPI :$PORT)   │    │ (ingestion, extraction,│   │
   │  └────────────────────┘    │  evaluation, default)  │   │
   │       ▲       │             └────────────┬───────────┘   │
   │       │       └── reads/writes ─────►    │               │
   │       │     /opt/render/.../data/{storage,faiss}         │
   │       │     (Render persistent disk, 1 GB)               │
   └───────┼─────────────────────────────────────────┼───────┘
           │                                         │
           ▼                                         ▼
   ┌──────────────────────┐                 ┌────────────────────┐
   │ Supabase (Postgres)  │                 │ vajans-redis       │
   │ Transaction pooler   │                 │ Celery broker +    │
   │ aws-1-ap-northeast-1 │                 │ result backend     │
   └──────────────────────┘                 └────────────────────┘
```

### Why the backend is a single service

Render disks cannot be shared across services, but both the FastAPI tier
(receives uploads, serves PDFs inline for the in-app viewer) and the Celery
worker (ingests PDFs, builds FAISS indexes) must read/write the same data
directories. Co-locating both processes via `honcho` keeps everything on one
disk without introducing S3.

## 2. One-time setup

### 2.1 Supabase

1. Open the project at <https://supabase.com/dashboard/project/kalihyqbvziypwhklhjc>.
2. Confirm the project is active (not paused).
3. **Database → Connect → Transaction pooler**: copy the connection string and
   confirm it matches the host hard-coded in `backend/app/db/session.py`:
   - `aws-1-ap-northeast-1.pooler.supabase.com:6543`
   - user: `postgres.kalihyqbvziypwhklhjc`
4. Schema is created automatically on first boot by `start.sh →
   migrate_to_supabase.py` (idempotent `Base.metadata.create_all`).

### 2.2 Render Blueprint

1. Push this repo (with `render.yaml`) to GitHub.
2. In the Render dashboard: **New → Blueprint** → connect the repo.
3. Render reads `render.yaml` and provisions:
   - `vajans-backend` (web, Python 3.12.3, 1 GB disk)
   - `vajans-redis` (free Redis)
   - `vajans-frontend` (static site)
4. Three secrets are flagged `sync: false` and **must be set manually** in the
   Render dashboard before the first deploy succeeds:

| Service          | Variable             | Value                                                                      |
|------------------|----------------------|----------------------------------------------------------------------------|
| vajans-backend   | `OPENROUTER_API_KEY` | the OpenRouter API key (`sk-or-...`)                                       |
| vajans-backend   | `ALLOWED_HOSTS`      | JSON array, e.g. `["https://vajans-frontend.onrender.com"]`                |
| vajans-frontend  | `VITE_API_BASE_URL`  | `https://vajans-backend.onrender.com/api` (replace with your backend URL)  |

`SECRET_KEY` is auto-generated by Render on first deploy
(`generateValue: true`).

### 2.3 First deploy

After the secrets are set, trigger a manual deploy on `vajans-backend` and
`vajans-frontend`. Watch the backend logs for:

```
[start.sh] env=production
[start.sh] running Supabase schema migration
✓ All tables created in Supabase
✓ Tables in Supabase (12): [...]
[start.sh] launching honcho (web + worker)
worker.1 | celery@... ready.
web.1    | INFO:     Uvicorn running on http://0.0.0.0:10000
```

`/api/health` should return `200 {"status":"ok"}` within seconds.
`/api/health/ready` should return `200` with `database:ok` and `redis:ok`.

## 3. Local development

Local keeps using the existing PostgreSQL on port 5432. No code change needed
to switch — the env var is the only switch:

```bash
# Local dev
ENVIRONMENT=development uvicorn app.main:app --reload      # in backend/
celery -A worker.celery_app worker --loglevel=info         # in backend/
npm run dev                                                # in frontend/

# Smoke against Supabase from the dev machine
ENVIRONMENT=production python3 migrate_to_supabase.py
```

## 4. Operational notes

**Cold-start latency.** Supabase free-tier projects pause after ~1 week of
inactivity; the first request after a pause takes ~10 s. Render's default
3 s health-check timeout would fail on `/api/health/ready`, so the blueprint
points the health check at `/api/health` (no DB / Redis touch) instead.

**Disk capacity.** The blueprint provisions 1 GB. PDFs land in
`data/storage/<job_id>/...` and FAISS indexes in `data/faiss`. Monitor disk
usage in the Render dashboard; expand by editing `disk.sizeGB` and
re-running the blueprint.

**FAISS rebuild.** FAISS indexes are rebuilt by the ingestion pipeline on
every job run, so losing them on a redeploy or scale-down is harmless.
**PDFs are NOT regenerated** — losing the disk means losing the source
documents. Take a Supabase snapshot + Render disk snapshot before any
destructive operation.

**Connection pooling.** The SQLAlchemy engine uses `NullPool` (mandatory for
Celery's per-task `asyncio.run()`). Each request opens a fresh asyncpg
connection through the Supabase pgbouncer, with UUID-named prepared
statements to defuse pgbouncer's transaction-mode statement collisions
(see comments in `backend/app/db/session.py`).

**Scaling out.** The current architecture is single-instance. If you need
to scale horizontally:
1. Implement S3 storage backend (stub exists in `app/services/storage.py`).
2. Switch `STORAGE_BACKEND=s3` and add the AWS env vars.
3. Split `vajans-backend` into separate `web` and `worker` Render services
   sharing the same S3 bucket.

---

## 5. Rollback

Each Render deploy is immutable; use the **Rollback** button on the deploy
to revert. The Supabase schema is forward-compatible (only `create_all`,
no destructive migrations), so backend code rollbacks are safe even after a
fresh table is created.
